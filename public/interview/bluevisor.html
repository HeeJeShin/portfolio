L1좋은 리더란? 본인은 리더인가요, 팔로워인가요?

좋은 리더 = 누가 무엇을 잘하는지 아는 사람중간 관리자 때 팀원이 잘하는 걸 맡김나는 상황에 맞게 — 리더일 땐 맡기고, 팔로워일 땐 근거로 제안
좋은 리더는 가장 잘하는 사람이 아니라, 누가 무엇을 잘하는지 알고 그 일을 맡기는 사람이라고 생각합니다. 저도 중간 관리자 역할을 할 때 팀원 의견을 먼저 듣고 각자 잘하는 일을 맡기려고 했습니다. 저는 상황에 맞춰 움직이는 편입니다. 리더일 때는 그렇게 맡기고, 팔로워일 때는 시키는 것만 하지 않고 근거를 가지고 먼저 제안합니다. 디자이너가 없던 어드민 프로젝트에서 UI 가이드를 먼저 만들어 제안한 것도 그런 경우였습니다.

L2개인적인 비전과 그것을 위한 노력은?

비전: 화면부터 서버까지 책임지는 시니어 풀스택 → 리더노력 1: 중구 — NestJS·DB·배포·테스트를 혼자노력 2: 서울사이버대 컴퓨터공학과 재학노력 3: 매일 공부한 걸 정리해 기록
화면부터 서버까지 책임질 수 있는 시니어 풀스택 개발자가 되고, 그다음에는 팀원이 잘하는 걸 살려 주는 리더가 되는 게 목표입니다. 그래서 실무에서 백엔드 팀이 맡던 부분을 직접 해 보려고, 중고차 가이드 '중구'를 NestJS와 PostgreSQL로 API, 인증, 테스트, 배포까지 혼자 만들어 운영하고 있습니다. 기초를 채우려고 서울사이버대 컴퓨터공학과에 다니고 있고, 공부한 내용은 매일 정리해서 기록으로 남기고 있습니다.

3가장 어려웠던 문제와 해결 과정

제일 어려웠던 건 원인보다 "설득"문제: 결제 직후 연결 끊기면 주문 완료 누락 (북키즈콘)진행 중인 사업은 바꾸기 어려움새 사업(스마트관광) 시작 때 제안개발자 + 사업담당자에게 직접결과: 상태 어긋남 없음
기술적인 원인보다, 결국 설득이 가장 어려웠습니다. O2MEET 북키즈콘 행사에서 결제 직후 모바일 연결이 끊기면 주문 완료 처리가 빠지는 문제가 있었습니다. 원인은 완료 처리를 프론트가 맡고 있어서, 연결이 끊기면 처리할 주체가 사라진다는 점이었습니다. 원인을 찾은 뒤에도 이미 진행 중인 사업의 결제 구조를 바꾸기는 쉽지 않았습니다. 그래서 새 사업인 스마트관광을 시작할 때 다시 제안했습니다. 같은 개발자뿐 아니라 사업담당자에게도 직접, 실제로 났던 이슈와 해결 방법을 설명했습니다. 그렇게 완료 처리를 서버가 맡는 구조로 바꿨고, 그 뒤로는 연결이 끊겨도 결제 상태가 어긋나지 않았습니다. 이 일로, 맞는 방법을 아는 것만큼 그 방법을 상대가 이해하는 말로 설명하는 게 중요하다는 걸 배웠습니다.

꼬리 "사업담당자에게는 어떻게 설명했나요?" → 기술 용어 대신 "결제는 됐는데 주문이 안 잡히는 고객이 생긴다"처럼 실제 피해로 설명했다고 답하기 (실제로 그렇게 말했는지 본인 기억대로).

4장애를 찾고 대응한 경험 / 모니터링

iOS Safari에서만 로그인 풀림실기기 재현 → ITP 원인쿠키+localStorage, 토큰 1시간배포 전 점검 항목에 추가(보조) 키오스크 디버깅 모드 · Sentry
서비스 시작 전 QA에서 iOS Safari만 로그인이 풀리는 문제가 있었습니다. 실기기로 재현해 보니 Safari의 ITP가 스크립트로 심은 쿠키를 지우는 게 원인이었습니다. 쿠키만 쓰면 ITP에 지워지고 localStorage만 쓰면 XSS에 노출되기 때문에, 둘에 함께 저장하고 복구 순서를 정했고 액세스 토큰은 1시간으로 짧게 둬 위험을 줄였습니다. 이후 Safari 확인을 배포 전 점검 항목에 넣었습니다. 로그를 볼 수 없는 현장 키오스크에서는 화면 상단을 다섯 번 누르면 오류 로그가 보이게 했고, 개인 서비스에는 Sentry를 붙여 오류를 추적하고 있습니다.

5LLM API를 연동해 본 경험

중구: Gemini = 추천만정보는 검증된 DB에서만4J: 도면 읽기는 AI, 계산은 코드기준: 틀리면 안 되는 건 AI에 안 맡김
두 번 써 봤습니다. 중구에서는 Gemini에게 조건에 맞는 차종·연식 추천만 맡기고, 고질병 같은 정보는 출처가 있는 DB에서만 보여 줬습니다. 사내 해커톤에서 만든 행사장 수용인원 계산 서비스에서도 Gemini는 도면에서 면적과 출입구만 읽고, 수용인원은 기준에 따라 코드가 계산하게 했습니다. 두 경우 모두 기준은 같았습니다. 틀리면 안 되는 값은 AI에 맡기지 않고, AI가 잘하는 부분만 맡기는 것입니다.

꼬리질문 "AI 답변 캐시·요청 제한은?" → 지금은 서버 메모리에 두었고, 사용자가 늘면 Redis로 옮겨야 한다고 정리해 둠(아직 안 함).

(Redis 30초 답) 지금은 서버가 한 대라 메모리에 두었습니다. 하지만 서버가 재시작되면 캐시와 요청 횟수가 초기화되고, 서버를 늘리면 서버마다 따로 세서 요청 제한이 뚫립니다. 그래서 사용자가 늘면 여러 서버가 함께 쓰는 Redis로 옮겨야 한다고 판단했습니다. Redis도 메모리 기반이라 영구 저장이 목적이라기보다, 상태를 서버 밖으로 빼서 공유하는 게 목적입니다.

메모리가 늘어나는 게 아니라 저장 위치가 앱 서버 → 별도 Redis 서버로 옮겨 가는 것. 대신 운영할 서버가 하나 늘어남(비용·관리).

6AI 코딩 도구를 어떻게 쓰나요

검색 노출이나 서버 렌더링을 노린 선택은 아니었습니다. 사용자 앱이 이미 Next.js였기 때문에, 어드민도 같은 스택으로 맞춰 모노레포 안에서 컴포넌트와 타입을 함께 쓰는 게 유지보수에 낫다고 판단했습니다. 다만 실제로는 어드민에서 Next.js의 서버 기능을 거의 쓰지 않았습니다. 그래서 다시 한다면, 어드민은 서버 없이 도는 React 앱으로 가볍게 만들고 공통 코드는 공유 패키지로 계속 같이 쓰는 방법도 비교해 보겠습니다.
SPA (에스피에이)가 뭐죠?Single Page Application. 처음에 페이지 하나와 자바스크립트를 받고, 그다음 화면 전환은 브라우저에서 자바스크립트가 다 그리는 방식입니다. React를 Vite로 만들면 보통 이렇게 됩니다. 서버가 필요 없어서 빌드한 파일만 올리면 배포가 끝납니다.
Next.js와 뭐가 다르죠?Next.js는 서버에서 화면을 미리 그려 줄 수 있는 대신, 그 기능을 쓰려면 서버(Node)를 띄워 둬야 합니다. 어드민은 검색 노출도 필요 없고 로그인한 직원만 쓰니까, 서버에서 미리 그릴 이유가 적었습니다.
공유 패키지가 뭐죠?한 저장소(모노레포) 안에 packages/shared 폴더를 두고, 거기에 공통 버튼·폼·테이블 컴포넌트와 API 타입을 넣은 것입니다. 사용자 앱과 어드민이 이걸 같이 가져다 써서, 한 번 고치면 두 앱에 같이 반영됩니다.
그래서 결론은?공유 패키지는 Next.js가 아니어도 쓸 수 있습니다. 그러니까 "코드 공유" 때문에 꼭 Next.js일 필요는 없었고, 어드민만 SPA로 만들었으면 서버 없이 더 가볍게 배포할 수 있었을 거라는 뜻입니다.

"SPA"라는 말이 입에 안 붙으면 "서버 없이 도는 React 앱"이라고만 말해도 됩니다. 물어보면 위 표 순서대로 설명.

두 상태의 성질이 달라서 나눴습니다. 서버에서 받은 데이터는 시간이 지나면 낡기 때문에 캐싱과 다시 받아오기가 필요한데, TanStack Query가 이걸 기본으로 해 줍니다. Redux로 하면 로딩·에러·캐시를 전부 직접 만들어야 합니다. 권한이나 선택한 프로젝트 같은 화면 상태는 Zustand에 두고 필요한 값만 구독하게 해서, 데이터가 어디서 바뀌는지 헷갈리지 않게 했습니다.

수정 후 목록 갱신은 실제로 새로고침으로 처리했습니다. invalidateQueries는 안 썼으니 "했다"고 하지 말고, "지금이라면 그 목록 캐시만 무효화하겠다"로 답하기.

TanStack Query서버에서 가져온 데이터를 담당. API를 불러서 받아 오고, 받아 온 걸 저장(캐싱)해 두었다가 낡으면 다시 받아 옴. 예: 신청 목록, 전시회 정보
Zustand (주스탠드)서버에서 읽어 오는 게 아니라, 브라우저(화면) 안에서만 쓰는 값을 담아 두는 저장소. 사용자가 화면에서 고른 것, 로그인 후 정해진 권한처럼 서버에 다시 물어볼 필요 없는 값. 예: 지금 선택한 프로젝트, 내 권한

T3토큰을 왜 쿠키와 localStorage 두 곳에 저장했나요?

쿠키만 쓰면 Safari의 ITP가 스크립트로 심은 쿠키를 지워서 로그인이 풀렸고, localStorage만 쓰면 XSS 공격에 토큰이 노출됩니다. 그래서 둘에 함께 저장하고 메모리, 쿠키, localStorage 순서로 복구하게 했습니다. localStorage의 위험은 액세스 토큰을 1시간으로 짧게 두고 리프레시로 재발급받는 방식으로 줄였습니다. 실기기에서 로그인이 유지되는 것으로 확인했습니다.
ITP (아이티피)가 뭐죠?Intelligent Tracking Prevention. Safari의 추적 방지 기능입니다. 광고 추적을 막으려고 쿠키를 제한하는데, 자바스크립트로 만든 쿠키는 수명을 짧게(최대 7일) 줄여 버립니다. 그래서 정상적인 로그인 쿠키까지 지워져 로그인이 풀렸습니다.
XSS (엑스에스에스)가 뭐죠?Cross-Site Scripting. 공격자가 페이지에 나쁜 스크립트를 몰래 심어 실행시키는 공격입니다. localStorage는 자바스크립트로 읽을 수 있어서, 스크립트가 실행되면 저장된 토큰을 훔쳐 갈 수 있습니다.
그래서 어떻게?쿠키(ITP에 지워질 수 있음)와 localStorage(XSS 위험)를 같이 써서 하나가 사라져도 복구하고, 훔쳐 가도 오래 못 쓰게 액세스 토큰을 1시간으로 짧게 둠.

T4Gemini 답을 그대로 안 보여 주고 DB에서만 보여 준 이유는?

돈이 걸린 판단에 쓰는 정보AI는 그럴듯하게 틀릴 수 있음AI = 추천, 정보 = 출처 있는 DB
중고차를 살지 말지 판단하는 데 쓰는 정보라, 틀리면 사용자가 돈으로 손해를 봅니다. AI는 그럴듯하게 틀린 답을 낼 수 있어서, 고질병 같은 정보는 출처가 있는 DB에서만 보여 주고 Gemini에게는 조건에 맞는 차종·연식 추천만 맡겼습니다. 틀리면 안 되는 값인지를 기준으로 AI가 맡을 범위를 정했습니다.
AI가 하는 일사용자가 말한 조건("출퇴근용, 유지비 적게")에 맞는 차종과 사기 좋은 연식 범위를 1~5개 고르고, 고른 이유를 적음
어디서 고르나프롬프트에 넣어 준 DB에 등록된 차 목록 안에서만 고르고, 그 차의 번호(carModelId)를 적게 함

T5조회 화면은 왜 ISR로 만들었나요?

무료 API 서버가 15분 쉬면 잠듦미리 만든 화면이라 바로 뜸관리자 승인 시 즉시 다시 만듦
API 서버를 무료 서버(Render)에 올렸는데, 15분 동안 요청이 없으면 잠들어서 첫 요청이 느립니다. 요청할 때마다 서버에서 그리면 사용자가 그 시간을 기다려야 해서, 조회 화면은 ISR로 미리 만들어 두고 서버가 잠들어 있어도 바로 뜨게 했습니다. 대신 관리자가 내용을 승인하면 저장된 화면을 바로 무효화해서 낡은 내용이 남지 않게 했습니다.
ISR (아이에스알)이 뭐죠?Incremental Static Regeneration. 화면을 미리 만들어 저장해 두고, 정해진 때에 그 화면만 새로 만드는 방식입니다. 사용자는 저장된 화면을 바로 받으니 빠르고, 내용이 바뀌면 그 페이지만 다시 만듭니다.
비유주문 들어올 때마다 요리하는 대신(SSR) 미리 만들어 진열해 두고(SSG), 메뉴가 바뀌면 그 메뉴만 다시 만들어 진열하는 것(ISR).
중구에서차종·리포트 조회 화면을 미리 만들어 둠 → API 서버가 잠들어 있어도 화면은 바로 뜸. 관리자가 고질병을 승인하면 그 페이지 저장본을 바로 버리고 새로 만듦.

T6MUI를 걷어내고 Tailwind로 바꾼 이유는?

마이그레이션 1차에서 MUI와 기존 CSS가 섞이면서, 어느 스타일이 이길지 예측하기 어려운 충돌이 계속 났습니다. MUI는 실행 중에 자바스크립트로 스타일을 만들어 넣어서 번들도 무거워집니다. Tailwind는 빌드할 때 필요한 클래스만 만들고 안 쓰는 건 지워 주기 때문에, 2차에서는 처음부터 Tailwind 하나로 통일했습니다. 결과적으로 쓰지 않는 CSS가 891KB에서 0KB가 된 것을 Lighthouse로 확인했습니다.

T7백엔드는 왜 NestJS로 했나요?

이미 쓰는 TypeScript → 언어 대신 백엔드 개념에 집중회사 백엔드(Spring)와 구조가 비슷모듈·컨트롤러·서비스로 나누는 틀이 정해져 있음
목표가 언어를 새로 배우는 것보다 서버·DB·인증·배포 같은 백엔드 개념을 직접 익히는 것이었습니다. 그래서 이미 쓰고 있던 TypeScript로 할 수 있는 NestJS를 골랐습니다. 또 전 회사 백엔드가 Java Spring이었는데, NestJS는 모듈·컨트롤러·서비스로 나누고 의존성을 주입하는 구조가 Spring과 비슷해서, 나중에 Spring으로 넓힐 때도 개념을 그대로 가져갈 수 있다고 판단했습니다. 실제로 둘을 나란히 놓고 정리해 뒀습니다.

F3[JS·브라우저] 쿠키, localStorage, sessionStorage 차이는?

쿠키: 요청마다 서버로 자동 전송 · httpOnly면 JS가 못 읽음localStorage: 브라우저에 계속 남음 · JS로 읽기 가능sessionStorage: 탭 닫으면 사라짐경험: Safari ITP + XSS 때문에 둘 다 씀(T3)
쿠키는 요청할 때마다 서버로 자동으로 함께 가고, httpOnly로 설정하면 자바스크립트가 읽을 수 없어 탈취에 강합니다. localStorage는 지우기 전까지 브라우저에 남아 있지만 자바스크립트로 읽을 수 있어 XSS에 약하고, sessionStorage는 탭을 닫으면 사라집니다. 저는 스마트관광에서 Safari ITP가 쿠키를 지워 로그인이 풀리는 문제를 겪어서, 쿠키와 localStorage에 함께 저장하고 액세스 토큰을 1시간으로 짧게 두는 방식으로 해결했습니다.

F4[손코딩] 문제를 받으면 어떻게 푸나요? (+ debounce 직접 구현)

문제를 내 말로 다시 말하기입력·출력 예시 하나 만들기단순한 방법 먼저 → 개선시간 복잡도 말하기자주 나옴: debounce·throttle
바로 코드를 쓰기보다, 먼저 문제를 제 말로 다시 말해서 이해한 게 맞는지 확인합니다. 그다음 입력과 출력 예시를 하나 만들고, 단순한 방법으로 먼저 풀어 본 뒤 더 나은 방법이 있는지 봅니다. 마지막으로 시간 복잡도를 말하고, 빈 배열 같은 예외 입력을 확인합니다.
// debounce: 마지막 입력 후 delay 동안 조용하면 한 번만 실행 (검색창 자동완성) function debounce(fn, delay) { let timer; return (...args) => { clearTimeout(timer); timer = setTimeout(() => fn(...args), delay); }; } // throttle: delay마다 최대 한 번만 실행 (스크롤 이벤트) function throttle(fn, delay) { let last = 0; return (...args) => { const now = Date.now(); if (now - last >= delay) { last = now; fn(...args); } }; }

debounce 안의 timer가 함수가 끝나도 살아 있는 건 클로저 때문 — "클로저가 뭐냐"로 이어질 수 있음: 함수가 만들어질 때의 바깥 변수를 기억하는 것. 배열 문제는 "두 번 도는 대신 객체(Map)에 담아 한 번에" → O(n²) → O(n)이 가장 흔한 개선.

이미지 최적화를 따로 맡아 본 적은 없습니다. 다만 성능을 개선할 때는 Lighthouse로 먼저 원인을 찾는 편이라, 이미지가 원인이라면 이렇게 하겠습니다. 첫째, WebP나 AVIF처럼 용량이 작은 포맷으로 바꿉니다. 둘째, 화면 크기에 맞는 해상도를 여러 개 두고 기기에 맞게 내려보냅니다. 셋째, 첫 화면 밖에 있는 이미지는 레이지 로딩으로 나중에 불러옵니다. 넷째, 이미지 크기를 미리 정해 두어 화면이 밀리지 않게 합니다. 실제로 마이그레이션에서는 쓰지 않는 자바스크립트와 CSS를 걷어내 LCP를 8초에서 0.8초로 줄였기 때문에, 이미지도 같은 방식으로 측정하고 개선할 수 있습니다.
레이지 로딩 (lazy loading)화면에 보일 때가 돼서야 불러오는 것. 첫 화면에 필요 없는 이미지를 미리 받지 않아 처음 뜨는 속도가 빨라짐. <img loading="lazy"> 한 줄로 가능, Next.js Image는 기본이 lazy
주의첫 화면 맨 위의 큰 이미지(LCP 대상)는 lazy로 두면 오히려 늦어짐 → 이건 먼저 불러오기(priority)
코드도 레이지 로딩이미지뿐 아니라 컴포넌트도 필요할 때 불러올 수 있음: React lazy, Next.js dynamic() → 처음 받는 자바스크립트가 줄어듦 (코드 스플리팅)

"주의" 줄까지 말하면 개념을 제대로 안다는 게 드러남. 써 본 적 없으면 "써 봤다"고 하지 말기.

F10[렌더링·성능] 지도에 마커가 수십~수백 개 찍혀 버벅이면 어떻게 하나요?

원인: 마커 하나하나가 DOM이라 많으면 그리기·이벤트가 무거움① 클러스터링(가까운 건 숫자 하나로)② 지금 보이는 영역 안의 것만③ 지도 이동 이벤트는 debounce④ 마커 객체 재사용 · 리렌더 줄이기
지도 마커를 직접 다뤄 본 적은 없지만, 원인은 마커 하나하나가 화면 요소라서 개수가 많으면 그리기와 이벤트 처리가 무거워지는 거라고 생각합니다. 그래서 그리는 개수 자체를 줄이는 방향으로 접근하겠습니다. 첫째, 가까운 마커는 클러스터링으로 묶어 숫자 하나로 보여 주고, 확대하면 풀어 줍니다. 둘째, 지금 화면에 보이는 영역 안의 식당만 그리고, 가능하면 서버에도 그 영역 좌표로 요청해서 받아 오는 데이터부터 줄입니다. 셋째, 지도를 움직일 때마다 요청하지 않도록 이동이 멈춘 뒤에 한 번만 요청하게 debounce를 겁니다. 넷째, 목록이 바뀔 때 마커를 전부 지우고 새로 만들지 않고, 바뀐 것만 추가하거나 지우게 합니다. 개선 여부는 개발자 도구의 Performance 탭으로 프레임이 떨어지는지 측정해서 확인하겠습니다.
클러스터링가까이 모인 마커를 원 하나 + 개수로 합쳐 보여 줌. 카카오맵 MarkerClusterer, 네이버 지도 클러스터 예제 등 지도 SDK가 대부분 지원
영역(bounds) 조회지도의 남서·북동 좌표를 서버에 보내서 그 안의 것만 받음. 서버는 위도·경도에 인덱스 → B4 인덱스와 연결
옆 목록도 길면가상 스크롤: 화면에 보이는 몇 줄만 실제로 그리고 스크롤에 맞춰 바꿔 끼움

debounce 코드는 F4에 있음. "직접 해 본 적은 없지만"으로 시작하고, 측정 방법으로 끝내기.

꼬리: debounce 시간은 어떻게 정하나요?두 가지 사이에서 고름 — 너무 짧으면 요청이 많아지고, 너무 길면 느리게 느껴짐. 사람이 "바로 반응한다"고 느끼는 한계가 대략 0.1~0.3초라 그 근처에서 시작.
보통 시작값검색 자동완성 200~300ms(타이핑 사이 간격보다 조금 길게) · 지도 이동 300~500ms(드래그가 끝났다고 볼 만큼) · 창 크기 조절 100~200ms
정하는 방법시작값을 두고 요청 수(네트워크 탭)와 체감을 같이 보고 조정. API 호출 한도나 비용이 크면 더 길게.
같이 하면 좋은 것늦게 온 이전 응답이 최신 결과를 덮어쓰지 않게, 새 요청을 보낼 때 이전 요청은 취소(AbortController)
(30초 답) 너무 짧으면 요청이 많아지고 너무 길면 느리게 느껴지기 때문에, 그 사이에서 정합니다. 사람이 바로 반응한다고 느끼는 0.1~0.3초 근처에서 시작해서, 검색은 300ms, 지도 이동은 드래그가 끝났다고 볼 수 있게 조금 더 길게 둡니다. 그다음 네트워크 탭에서 요청 수와 실제 체감을 같이 보며 조정하고, API 호출 한도가 있으면 더 길게 잡습니다.

N1DOM과 가상 DOM은 무엇이고, 가상 DOM은 뭐가 좋은가요? (모의 26점)

DOM = 브라우저가 HTML을 객체 나무로 만든 것가상 DOM = 그 복사본을 JS 메모리에바뀌기 전/후를 비교(diff) → 바뀐 곳만 실제 DOM에 반영장점: 직접 여러 번 고치는 것보다 reflow 줄이고, 코드가 단순
DOM은 브라우저가 HTML을 읽어서 만든 객체 나무이고, 자바스크립트는 이걸 고쳐서 화면을 바꿉니다. 그런데 DOM을 고칠 때마다 레이아웃 계산과 다시 그리기가 일어날 수 있어 비용이 큽니다. 가상 DOM은 그 구조를 자바스크립트 메모리에 가볍게 복사해 둔 것입니다. React는 상태가 바뀌면 새 가상 DOM을 만들고 이전 것과 비교해서, 실제로 바뀐 부분만 한 번에 실제 DOM에 반영합니다. 그래서 개발자는 "이 상태면 화면이 이렇다"만 선언하면 되고, 어디를 어떻게 고칠지는 React가 최소한으로 처리해 줍니다.

경험 연결: JSP·jQuery에서는 DOM을 직접 찾아 고쳤고, React로 옮기면서 상태만 바꾸면 화면이 따라오는 방식으로 바뀜. "가상 DOM이 항상 더 빠르다"는 틀린 말 — 비교 비용이 있음. 장점은 "바뀐 곳만 모아서 반영 + 선언형 코드".

N2reflow와 repaint 차이, 무엇이 reflow를 일으키고 어떻게 줄이나요? (모의 27점)

reflow = 위치·크기 다시 계산 (무거움)repaint = 색만 다시 칠함 (가벼움)일으키는 것: width·height·margin 변경, 요소 추가·삭제, 글자 크기, offsetHeight 읽기줄이기: transform·opacity로 움직이기, 한 번에 모아서 바꾸기, 이미지 크기 미리 지정
reflow는 요소의 위치나 크기가 바뀌어서 레이아웃을 다시 계산하는 것이고, repaint는 색이나 그림자처럼 모양만 바뀌어서 다시 칠하기만 하는 것입니다. reflow가 일어나면 repaint도 따라오기 때문에 더 무겁습니다. 너비나 여백을 바꾸거나, 요소를 추가·삭제하거나, offsetHeight처럼 크기를 읽는 코드도 reflow를 일으킵니다. 그래서 애니메이션은 레이아웃에 영향을 주지 않는 transform과 opacity로 하고, 스타일은 하나씩 바꾸지 않고 클래스로 한 번에 바꾸며, 이미지는 크기를 미리 정해서 나중에 들어오며 화면이 밀리지 않게 합니다.

"O2MEET에서 reflow 최적화를 했나요?" → 따로 reflow를 측정해 고친 적은 없다고 솔직히. 다만 CLS 0.225 → 0은 레이아웃이 나중에 밀리는 걸 없앤 결과라 관련 있다고 연결.

N3브라우저 캐시는 어떻게 동작하고, 잘 쓰면 뭐가 좋나요? (모의 28점)

서버가 응답 헤더로 "얼마나 저장해도 되는지" 알려 줌 (Cache-Control: max-age)기간 안이면 서버에 안 묻고 바로 사용기간 지나면 "바뀌었나요?" 물어봄 (ETag) → 안 바뀌었으면 304, 본문 없이파일 이름에 해시 → 바뀌면 새 이름이라 오래 캐시해도 안전
브라우저 캐시는 서버가 응답 헤더로 이 파일을 얼마나 저장해 둬도 되는지 알려 주면, 그 기간 동안은 서버에 다시 묻지 않고 저장된 걸 바로 쓰는 방식입니다. 기간이 지나면 서버에 바뀌었는지만 물어보고, 안 바뀌었으면 서버는 내용 없이 304만 보내서 다시 받는 양이 줄어듭니다. 잘 쓰면 다시 방문할 때 화면이 빠르게 뜨고, 서버와 네트워크 부담도 줄어듭니다. 보통 이미지나 빌드된 JS·CSS처럼 파일 이름에 해시가 붙는 정적 파일은 오래 저장하고, 내용이 자주 바뀌는 HTML이나 API 응답은 짧게 두거나 매번 확인하게 합니다.

Next.js는 빌드한 JS·CSS 파일 이름에 해시를 붙여서 오래 캐시해도 안전하게 해 줌 — 이걸 알고 있으면 충분.

B1REST API는 어떻게 설계했나요? 상태 코드는 어떻게 나눴나요?

주소 = 자원(명사), 동작 = 메서드(GET·POST·PATCH·DELETE)400 잘못된 요청 · 401 로그인 필요 · 403 권한 없음404 없음 · 409 이미 바뀜(충돌) · 500 서버 오류NestJS: 컨트롤러(주소 받기) / 서비스(실제 일) 분리
주소는 자원 이름으로 두고, 조회·생성·수정·삭제는 HTTP 메서드로 나눴습니다. 예를 들어 고질병은 /issues 아래에 두고, 상태를 바꾸는 요청은 따로 받았습니다. 상태 코드는 입력이 잘못되면 400, 로그인이 안 됐으면 401, 로그인은 했지만 권한이 없으면 403, 다른 사람이 먼저 바꿔서 충돌하면 409로 나눠서, 화면에서 상황에 맞는 안내를 보여 줄 수 있게 했습니다. NestJS에서는 주소를 받는 컨트롤러와 실제 일을 하는 서비스를 나누고, 기능별로 모듈로 묶었습니다.

401과 403 차이가 가장 자주 나옴: 401 = 누군지 모름(로그인 필요), 403 = 누군지는 아는데 권한 없음.

B2로그인·권한은 어떻게 구현했나요?

구글 로그인 → 구글 토큰을 서버가 구글 공개키로 검증서버가 자기 토큰(JWT) 발급 · Authorization: Bearer로 보냄역할: ADMIN · EDITOR · USER역할은 매 요청 DB에서 다시 확인 (토큰 발급 후 바뀔 수 있어서)Guard로 주소마다 권한 검사
구글 로그인을 붙였는데, 화면에서 받은 구글 토큰을 그대로 믿지 않고 서버가 구글의 공개키로 서명과 발급자를 검증합니다. 검증되면 서버가 자체 JWT를 발급하고, 화면은 요청할 때마다 Authorization 헤더에 담아 보냅니다. 권한은 ADMIN, EDITOR, USER로 나눴고, NestJS의 Guard로 주소마다 필요한 역할을 검사했습니다. 토큰을 발급한 뒤에 역할이 바뀔 수 있어서, 토큰 안의 역할만 믿지 않고 요청마다 DB의 현재 역할을 다시 확인하게 했습니다.
JWT (제이더블유티)서버가 서명한 출입증. 서버가 따로 저장하지 않아도 서명으로 진짜인지 확인 가능. 대신 한 번 발급하면 만료 전까지 취소가 어려움 → 그래서 역할은 DB에서 다시 확인
세션과 차이세션은 서버가 로그인 정보를 저장해 두고 쿠키로 번호만 줌 → 바로 끊기 쉽지만 서버가 상태를 들고 있어야 함

B3두 사람이 동시에 같은 데이터를 바꾸면 어떻게 되나요? (동시성)

"내가 본 상태 그대로일 때만" 바꾸기WHERE id = ? AND status = (내가 본 상태)바뀐 행이 0개면 → 누가 먼저 바꿈 → 409상태 변경 + 이력 기록을 한 트랜잭션
고질병을 승인할 때 두 관리자가 동시에 누르는 경우를 생각했습니다. 그래서 상태를 바꿀 때 "내가 화면에서 본 상태 그대로일 때만" 바꾸도록 조건을 걸었습니다. 먼저 누른 사람이 상태를 바꾸면, 뒤에 누른 사람의 조건은 맞지 않아 바뀐 행이 0개가 되고, 이때 409를 돌려주며 새로고침하라고 안내합니다. 내용 수정도 마지막 수정 시각이 같을 때만 저장되게 했습니다. 그리고 상태 변경과 이력 기록은 한 트랜잭션으로 묶어서 둘 중 하나만 남는 일이 없게 했습니다.

이 방식 이름: 낙관적 잠금(일단 진행하고, 저장할 때 충돌을 확인). 반대는 비관적 잠금(먼저 잠그고 다른 사람은 기다림) — 충돌이 드문 관리 화면이라 낙관적 방식이 맞다고 판단.

B4DB 인덱스는 무엇이고, 어디에 걸었나요?

인덱스 = 책 뒤의 찾아보기조회는 빨라지고, 쓰기는 조금 느려짐 · 공간 더 씀자주 찾는 조건에만: 차종 ID, (고질병, 작성 시각)
인덱스는 책 뒤의 찾아보기처럼, 전체를 다 훑지 않고 원하는 행을 바로 찾게 해 주는 장치입니다. 조회는 빨라지지만 데이터를 쓸 때마다 인덱스도 고쳐야 해서 쓰기가 조금 느려지고 공간도 더 씁니다. 그래서 중구에서는 자주 쓰는 조회 조건에만 걸었습니다. 차종별로 고질병을 찾는 경우가 많아 차종 ID에, 고질병별 이력은 최신순으로 보니까 고질병과 작성 시각을 묶어서 인덱스를 걸었습니다.

B5DB 스키마가 바뀌면 운영 데이터는 어떻게 지키나요? (마이그레이션)

Prisma로 스키마 변경을 마이그레이션 파일로 남기고, API 서버가 켜질 때 자동으로 적용되게 했습니다. 자동으로 적용되는 만큼, 운영 데이터를 지우는 변경은 하지 않는다는 규칙을 문서에 적어 뒀습니다. 컬럼 이름을 바꿔야 하면 바로 바꾸지 않고, 새 컬럼을 추가하고 값을 옮긴 뒤 나중에 정리하는 식으로 진행합니다.

B6캐시와 요청 제한은 왜, 어떻게 했나요?

B7CORS는 무엇이고 어떻게 설정했나요?

다른 주소(origin)에서 오는 요청을 브라우저가 막는 규칙화면(Vercel)과 API(Render) 주소가 다름서버가 허용할 화면 주소만 지정 (WEB_ORIGIN)서버끼리 요청에는 적용 안 됨 — 브라우저 규칙
CORS는 브라우저가 다른 주소에서 오는 요청을 기본적으로 막고, 서버가 허용한 주소만 통과시키는 규칙입니다. 중구는 화면이 Vercel, API가 Render로 주소가 달라서, API 서버에 화면 주소만 허용하도록 설정했습니다. 그 주소는 환경변수로 두었는데, Vercel 주소가 배포해야 생겨서 Render를 먼저 올리고 Vercel 주소를 받아 다시 넣는 순서가 필요했습니다.

CSP(콘텐츠 보안 정책)와 헷갈리지 않기: CORS = 누가 내 API를 부를 수 있나, CSP = 내 페이지가 어떤 스크립트를 실행할 수 있나.
