예상 질문

11분 자기소개

사람인 자소서 제목과 맞춤: "소통을 중요하게 생각하는 개발자"① 화면으로 소통 — UI 가이드 먼저② 근거로 설득 — 결제 구조, 사업담당자까지③ 실패를 회고해 다시 — 마이그레이션 1차 중단 → 2차 45 → 99
안녕하세요, 풀스택 개발자로 지원한 신희제입니다. 저는 소통을 중요하게 생각하는 개발자입니다. 저는 일할 때 세 가지를 중요하게 생각합니다. 첫째, 제가 잘하는 방식으로 소통합니다. 말로만 설명하기보다 화면을 직접 만들어 보여 주는 편입니다. 디자이너가 없던 어드민 프로젝트에서도 UI 가이드 화면을 먼저 만들어, 사업부서와 그 화면을 보며 방향을 맞췄습니다. 둘째, 근거로 설득합니다. 결제 직후 연결이 끊기면 주문이 빠지는 문제가 있었을 때, 실제로 났던 이슈를 근거로 개발자뿐 아니라 사업담당자에게도 직접 설명해 결제 완료 처리를 서버로 옮겼습니다. 셋째, 실패를 사람 탓으로 돌리지 않습니다. 같은 실수가 반복되면 테스트를 자동화해서 구조적으로 다시 나오지 않게 막고, 실패했을 때는 회고로 원인을 정리합니다. 마이그레이션 1차가 중단됐을 때도 회고한 내용을 바탕으로, 2차에서는 프로젝트 구조부터 먼저 잡고 시작했습니다. 블루바이저에서도 이렇게 소통하며 함께 문제를 푸는 개발자로 일하겠습니다.

약 50~60초. 사람인 자기소개서의 소제목(화면으로 소통 / 근거로 설득 / 실패를 회고해 다시 해냄)과 같은 순서라, 면접관이 서류와 비교해도 일관됨. 결제 설득은 3번, 협업은 9번에서 자세히.

2지원동기

공고에서 본 것: 웹 플랫폼 + 백오피스 + 인프라까지AI 기능을 사용자에게 전달내가 해 온 범위와 같음
공고에서 서비스 단의 프론트엔드·백엔드·인프라 운영까지 폭넓게 참여하고, AI 기술이 사용자에게 자연스럽게 전달되도록 만든다는 내용을 보고 지원했습니다. 저는 실무에서 사용자 화면과 어드민을 함께 만들어 왔고, 퇴사 후에는 API·DB·배포·모니터링까지 혼자 운영해 봤습니다. 특히 중구에서 Gemini 답변을 그대로 보여 주지 않고 DB와 역할을 나눠 신뢰할 수 있게 만든 경험이, AI 서비스를 사용자에게 전달하는 이 자리의 일과 맞닿아 있다고 생각했습니다.

하이버프 서비스를 써 본 적이 없으면 "써 봤다"고 하지 말고 "공고에서 봤다"로 말하기. 지금 보는 AI 면접 자체가 하이버프 AI 인터뷰라는 점은 마지막에 한 줄 정도로만.

3가장 어려웠던 문제와 해결 과정

제일 어려웠던 건 원인보다 "설득"문제: 결제 직후 연결 끊기면 주문 완료 누락 (북키즈콘)진행 중인 사업은 바꾸기 어려움새 사업(스마트관광) 시작 때 제안개발자 + 사업담당자에게 직접결과: 상태 어긋남 없음
기술적인 원인보다, 결국 설득이 가장 어려웠습니다. O2MEET 북키즈콘 행사에서 결제 직후 모바일 연결이 끊기면 주문 완료 처리가 빠지는 문제가 있었습니다. 원인은 완료 처리를 프론트가 맡고 있어서, 연결이 끊기면 처리할 주체가 사라진다는 점이었습니다. 원인을 찾은 뒤에도 이미 진행 중인 사업의 결제 구조를 바꾸기는 쉽지 않았습니다. 그래서 새 사업인 스마트관광을 시작할 때 다시 제안했습니다. 같은 개발자뿐 아니라 사업담당자에게도 직접, 실제로 났던 이슈와 해결 방법을 설명했습니다. 그렇게 완료 처리를 서버가 맡는 구조로 바꿨고, 그 뒤로는 연결이 끊겨도 결제 상태가 어긋나지 않았습니다. 이 일로, 맞는 방법을 아는 것만큼 그 방법을 상대가 이해하는 말로 설명하는 게 중요하다는 걸 배웠습니다.

꼬리 "사업담당자에게는 어떻게 설명했나요?" → 기술 용어 대신 "결제는 됐는데 주문이 안 잡히는 고객이 생긴다"처럼 실제 피해로 설명했다고 답하기 (실제로 그렇게 말했는지 본인 기억대로).

4장애를 찾고 대응한 경험 / 모니터링

iOS Safari에서만 로그인 풀림실기기 재현 → ITP 원인쿠키+localStorage, 토큰 1시간배포 전 점검 항목에 추가(보조) 키오스크 디버깅 모드 · Sentry
서비스 시작 전 QA에서 iOS Safari만 로그인이 풀리는 문제가 있었습니다. 실기기로 재현해 보니 Safari의 ITP가 스크립트로 심은 쿠키를 지우는 게 원인이었습니다. 쿠키만 쓰면 ITP에 지워지고 localStorage만 쓰면 XSS에 노출되기 때문에, 둘에 함께 저장하고 복구 순서를 정했고 액세스 토큰은 1시간으로 짧게 둬 위험을 줄였습니다. 이후 Safari 확인을 배포 전 점검 항목에 넣었습니다. 로그를 볼 수 없는 현장 키오스크에서는 화면 상단을 다섯 번 누르면 오류 로그가 보이게 했고, 개인 서비스에는 Sentry를 붙여 오류를 추적하고 있습니다.

5LLM API를 연동해 본 경험

중구: Gemini = 추천만정보는 검증된 DB에서만4J: 도면 읽기는 AI, 계산은 코드기준: 틀리면 안 되는 건 AI에 안 맡김
두 번 써 봤습니다. 중구에서는 Gemini에게 조건에 맞는 차종·연식 추천만 맡기고, 고질병 같은 정보는 출처가 있는 DB에서만 보여 줬습니다. 사내 해커톤에서 만든 행사장 수용인원 계산 서비스에서도 Gemini는 도면에서 면적과 출입구만 읽고, 수용인원은 기준에 따라 코드가 계산하게 했습니다. 두 경우 모두 기준은 같았습니다. 틀리면 안 되는 값은 AI에 맡기지 않고, AI가 잘하는 부분만 맡기는 것입니다.

꼬리질문 "AI 답변 캐시·요청 제한은?" → 지금은 서버 메모리에 두었고, 사용자가 늘면 Redis로 옮겨야 한다고 정리해 둠(아직 안 함).

(Redis 30초 답) 지금은 서버가 한 대라 메모리에 두었습니다. 하지만 서버가 재시작되면 캐시와 요청 횟수가 초기화되고, 서버를 늘리면 서버마다 따로 세서 요청 제한이 뚫립니다. 그래서 사용자가 늘면 여러 서버가 함께 쓰는 Redis로 옮겨야 한다고 판단했습니다. Redis도 메모리 기반이라 영구 저장이 목적이라기보다, 상태를 서버 밖으로 빼서 공유하는 게 목적입니다.

메모리가 늘어나는 게 아니라 저장 위치가 앱 서버 → 별도 Redis 서버로 옮겨 가는 것. 대신 운영할 서버가 하나 늘어남(비용·관리).

6AI 코딩 도구를 어떻게 쓰나요

Claude Code 실무 사용CLAUDE.md에 테스트 방법 공유Vitest 216개 · 중구 테스트 72개만든 사람 상관없이 같은 검증
Claude Code를 실무와 개인 프로젝트에서 씁니다. 다만 AI가 만든 코드를 그대로 믿지 않도록 검증 기준을 먼저 두는 편입니다. 어드민 프로젝트에서는 팀원 모두 Claude Code를 써서, CLAUDE.md에 테스트 실행 방법을 적어 두고 누가 만든 코드든 같은 방식으로 검증하게 했습니다. 테스트는 Vitest로 216개를 시작부터 설정했고, 중구는 단위 테스트와 E2E 테스트를 통과해야만 배포되게 했습니다.

꼬리 "단위 테스트와 E2E는 뭐가 다른가요?" / "테스트는 뭘 기준으로 짰나요?"

Vitest (비테스트) · 단위 테스트함수·훅 하나를 따로 떼서 입력 → 결과가 맞는지 확인. 빠르고 많이 돌릴 수 있음. 어드민 216개(유틸·훅·핵심 폼 로직), 중구 64개.
Playwright (플레이라이트) · E2E실제 브라우저를 띄워 사용자가 화면을 처음부터 끝까지 쓰는 흐름을 확인. 느리지만 실제 사용과 가장 가까움. 중구 8개.
둘 다 쓰는 이유단위 테스트는 부품이 맞는지, E2E는 부품을 이어 붙였을 때 실제로 되는지를 봄. 빠른 단위 테스트를 많이, 느린 E2E는 핵심 흐름만.
기준커버리지(몇 % 덮었나)보다 고친 곳 때문에 다른 곳이 깨지는 걸(회귀) 막는 것.
배포와 연결GitHub Actions(깃허브 액션)에서 테스트가 하나라도 실패하면 배포가 안 됨.
(30초 답) 단위 테스트는 함수나 훅 하나를 떼서 결과가 맞는지 빠르게 확인하는 거고, E2E는 실제 브라우저로 사용자 흐름을 처음부터 끝까지 확인하는 겁니다. 단위 테스트는 빠르니까 많이 두고, E2E는 느리니까 핵심 흐름만 뒀습니다. 기준은 커버리지 숫자보다, 한 곳을 고쳤을 때 다른 곳이 깨지지 않는지를 막는 것이었습니다.

"AI가 짠 테스트는 어떻게 믿나요?" → 테스트 통과 여부와 실제 화면 동작이 같은지 직접 확인. 공통 규칙은 CLAUDE.md에 먼저 정해 두고 AI가 그걸 지켰는지 봄. (일부러 코드를 깨뜨려 테스트가 실패하는지 확인하는 방법은 실제로 해 봤을 때만 말하기)

7PHP·Python 경험이 없는데 괜찮나요? (약점 질문)

솔직히 실무 경험 없음대신 JSP 레거시 4년 = 남의 코드 읽고 고치기NestJS 혼자 익혀 배포까지입사 후 기존 코드부터 읽기
솔직히 PHP와 Python으로 실무 백엔드를 해 보지는 않았습니다. 다만 두 가지는 자신 있습니다. 첫째, 4년간 JSP·jQuery 레거시를 운영하면서 남이 만든 코드를 읽고 고치는 일을 계속 해 왔습니다. 둘째, 실무에서 안 써 본 NestJS·PostgreSQL을 혼자 익혀 인증·권한·배포까지 운영하고 있습니다. 언어보다 API 설계, 트랜잭션, 테스트 같은 기준이 더 중요하다고 생각해서, 입사하면 기존 코드부터 읽으며 빠르게 맞추겠습니다.

Python·PHP를 "조금 해 봤다"고 부풀리지 않기. 통합 면접에서 기술 검증이 따로 있습니다.

트랜잭션이 뭐죠?속도가 아니라 "여러 DB 작업을 하나로 묶어서, 전부 성공하거나 전부 취소되게 하는 것"입니다. 중간에 하나라도 실패하면 앞에서 한 것까지 되돌립니다.
쉬운 예계좌 이체: A 계좌에서 빼기 + B 계좌에 넣기. 빼기만 되고 넣기가 실패하면 돈이 사라지니까, 둘을 한 트랜잭션으로 묶습니다.
내 경험 (중구)고질병 초안을 승인할 때 상태 변경(검토 → 승인)과 이력 기록을 한 트랜잭션으로 묶었습니다. 상태만 바뀌고 이력이 안 남는 일이 없게요. 두 관리자가 동시에 승인하면 한 명은 409(이미 처리됨) 응답을 받게 했습니다.

"언어보다 API 설계·트랜잭션·테스트가 중요하다" = 문법은 언어마다 달라도, 데이터가 어긋나지 않게 묶고 검증하는 기준은 같다는 뜻.

T1어드민은 검색에 안 나와도 되는데 왜 Next.js로 했나요?

SSR 때문이 아님 (이걸 먼저 말하기)사용자 앱이 이미 Next.js모노레포로 두 앱이 코드 공유
검색 노출이나 서버 렌더링을 노린 선택은 아니었습니다. 사용자 앱이 이미 Next.js였기 때문에, 어드민도 같은 스택으로 맞춰 모노레포 안에서 컴포넌트와 타입을 함께 쓰는 게 유지보수에 낫다고 판단했습니다. 다만 실제로는 어드민에서 Next.js의 서버 기능을 거의 쓰지 않았습니다. 그래서 다시 한다면, 어드민은 서버 없이 도는 React 앱으로 가볍게 만들고 공통 코드는 공유 패키지로 계속 같이 쓰는 방법도 비교해 보겠습니다.
SPA (에스피에이)가 뭐죠?Single Page Application. 처음에 페이지 하나와 자바스크립트를 받고, 그다음 화면 전환은 브라우저에서 자바스크립트가 다 그리는 방식입니다. React를 Vite로 만들면 보통 이렇게 됩니다. 서버가 필요 없어서 빌드한 파일만 올리면 배포가 끝납니다.
Next.js와 뭐가 다르죠?Next.js는 서버에서 화면을 미리 그려 줄 수 있는 대신, 그 기능을 쓰려면 서버(Node)를 띄워 둬야 합니다. 어드민은 검색 노출도 필요 없고 로그인한 직원만 쓰니까, 서버에서 미리 그릴 이유가 적었습니다.
공유 패키지가 뭐죠?한 저장소(모노레포) 안에 packages/shared 폴더를 두고, 거기에 공통 버튼·폼·테이블 컴포넌트와 API 타입을 넣은 것입니다. 사용자 앱과 어드민이 이걸 같이 가져다 써서, 한 번 고치면 두 앱에 같이 반영됩니다.
그래서 결론은?공유 패키지는 Next.js가 아니어도 쓸 수 있습니다. 그러니까 "코드 공유" 때문에 꼭 Next.js일 필요는 없었고, 어드민만 SPA로 만들었으면 서버 없이 더 가볍게 배포할 수 있었을 거라는 뜻입니다.

"SPA"라는 말이 입에 안 붙으면 "서버 없이 도는 React 앱"이라고만 말해도 됩니다. 물어보면 위 표 순서대로 설명.

T2TanStack Query와 Zustand는 왜 나눠 썼나요?

서버 데이터: 시간이 지나면 낡음 → 캐싱이 필요화면 상태: 권한·선택한 프로젝트한곳에 넣으면 결합도↑
두 상태의 성질이 달라서 나눴습니다. 서버에서 받은 데이터는 시간이 지나면 낡기 때문에 캐싱과 다시 받아오기가 필요한데, TanStack Query가 이걸 기본으로 해 줍니다. Redux로 하면 로딩·에러·캐시를 전부 직접 만들어야 합니다. 권한이나 선택한 프로젝트 같은 화면 상태는 Zustand에 두고 필요한 값만 구독하게 해서, 데이터가 어디서 바뀌는지 헷갈리지 않게 했습니다.

수정 후 목록 갱신은 실제로 새로고침으로 처리했습니다. invalidateQueries는 안 썼으니 "했다"고 하지 말고, "지금이라면 그 목록 캐시만 무효화하겠다"로 답하기.

TanStack Query서버에서 가져온 데이터를 담당. API를 불러서 받아 오고, 받아 온 걸 저장(캐싱)해 두었다가 낡으면 다시 받아 옴. 예: 신청 목록, 전시회 정보
Zustand (주스탠드)서버에서 읽어 오는 게 아니라, 브라우저(화면) 안에서만 쓰는 값을 담아 두는 저장소. 사용자가 화면에서 고른 것, 로그인 후 정해진 권한처럼 서버에 다시 물어볼 필요 없는 값. 예: 지금 선택한 프로젝트, 내 권한
"필요한 값만 구독"이란?컴포넌트가 저장소 전체가 아니라 자기가 쓰는 값 하나만 지켜봄. 그 값이 바뀔 때만 다시 그려져서, 상관없는 화면까지 다시 그려지지 않음

T3토큰을 왜 쿠키와 localStorage 두 곳에 저장했나요?

쿠키만: Safari ITP가 지움localStorage만: XSS에 노출둘에 저장 + 복구 순서액세스 토큰 1시간
쿠키만 쓰면 Safari의 ITP가 스크립트로 심은 쿠키를 지워서 로그인이 풀렸고, localStorage만 쓰면 XSS 공격에 토큰이 노출됩니다. 그래서 둘에 함께 저장하고 메모리, 쿠키, localStorage 순서로 복구하게 했습니다. localStorage의 위험은 액세스 토큰을 1시간으로 짧게 두고 리프레시로 재발급받는 방식으로 줄였습니다. 실기기에서 로그인이 유지되는 것으로 확인했습니다.
ITP (아이티피)가 뭐죠?Intelligent Tracking Prevention. Safari의 추적 방지 기능입니다. 광고 추적을 막으려고 쿠키를 제한하는데, 자바스크립트로 만든 쿠키는 수명을 짧게(최대 7일) 줄여 버립니다. 그래서 정상적인 로그인 쿠키까지 지워져 로그인이 풀렸습니다.
XSS (엑스에스에스)가 뭐죠?Cross-Site Scripting. 공격자가 페이지에 나쁜 스크립트를 몰래 심어 실행시키는 공격입니다. localStorage는 자바스크립트로 읽을 수 있어서, 스크립트가 실행되면 저장된 토큰을 훔쳐 갈 수 있습니다.
그래서 어떻게?쿠키(ITP에 지워질 수 있음)와 localStorage(XSS 위험)를 같이 써서 하나가 사라져도 복구하고, 훔쳐 가도 오래 못 쓰게 액세스 토큰을 1시간으로 짧게 둠.

T4Gemini 답을 그대로 안 보여 주고 DB에서만 보여 준 이유는?

돈이 걸린 판단에 쓰는 정보AI는 그럴듯하게 틀릴 수 있음AI = 추천, 정보 = 출처 있는 DB
중고차를 살지 말지 판단하는 데 쓰는 정보라, 틀리면 사용자가 돈으로 손해를 봅니다. AI는 그럴듯하게 틀린 답을 낼 수 있어서, 고질병 같은 정보는 출처가 있는 DB에서만 보여 주고 Gemini에게는 조건에 맞는 차종·연식 추천만 맡겼습니다. 틀리면 안 되는 값인지를 기준으로 AI가 맡을 범위를 정했습니다.
AI가 하는 일사용자가 말한 조건("출퇴근용, 유지비 적게")에 맞는 차종과 사기 좋은 연식 범위를 1~5개 고르고, 고른 이유를 적음
어디서 고르나프롬프트에 넣어 준 DB에 등록된 차 목록 안에서만 고르고, 그 차의 번호(carModelId)를 적게 함
AI가 안 하는 일특정 차종의 고질병 단정 · 금액(시세를 모르니까). 주의할 점은 주행거리·소모품 이력 같은 일반 확인 사항만
서버가 다시 확인답은 정해진 JSON 모양으로만 받고, 고른 차 번호와 연식이 DB에 실제로 있는지 서버가 다시 맞춰 봄

T5조회 화면은 왜 ISR로 만들었나요?

무료 API 서버가 15분 쉬면 잠듦미리 만든 화면이라 바로 뜸관리자 승인 시 즉시 다시 만듦
API 서버를 무료 서버(Render)에 올렸는데, 15분 동안 요청이 없으면 잠들어서 첫 요청이 느립니다. 요청할 때마다 서버에서 그리면 사용자가 그 시간을 기다려야 해서, 조회 화면은 ISR로 미리 만들어 두고 서버가 잠들어 있어도 바로 뜨게 했습니다. 대신 관리자가 내용을 승인하면 저장된 화면을 바로 무효화해서 낡은 내용이 남지 않게 했습니다.
ISR (아이에스알)이 뭐죠?Incremental Static Regeneration. 화면을 미리 만들어 저장해 두고, 정해진 때에 그 화면만 새로 만드는 방식입니다. 사용자는 저장된 화면을 바로 받으니 빠르고, 내용이 바뀌면 그 페이지만 다시 만듭니다.
비유주문 들어올 때마다 요리하는 대신(SSR) 미리 만들어 진열해 두고(SSG), 메뉴가 바뀌면 그 메뉴만 다시 만들어 진열하는 것(ISR).
중구에서차종·리포트 조회 화면을 미리 만들어 둠 → API 서버가 잠들어 있어도 화면은 바로 뜸. 관리자가 고질병을 승인하면 그 페이지 저장본을 바로 버리고 새로 만듦.

마이그레이션 1차에서 MUI와 기존 CSS가 섞이면서, 어느 스타일이 이길지 예측하기 어려운 충돌이 계속 났습니다. MUI는 실행 중에 자바스크립트로 스타일을 만들어 넣어서 번들도 무거워집니다. Tailwind는 빌드할 때 필요한 클래스만 만들고 안 쓰는 건 지워 주기 때문에, 2차에서는 처음부터 Tailwind 하나로 통일했습니다. 결과적으로 쓰지 않는 CSS가 891KB에서 0KB가 된 것을 Lighthouse로 확인했습니다.

T7백엔드는 왜 NestJS로 했나요?

이미 쓰는 TypeScript → 언어 대신 백엔드 개념에 집중회사 백엔드(Spring)와 구조가 비슷모듈·컨트롤러·서비스로 나누는 틀이 정해져 있음
목표가 언어를 새로 배우는 것보다 서버·DB·인증·배포 같은 백엔드 개념을 직접 익히는 것이었습니다. 그래서 이미 쓰고 있던 TypeScript로 할 수 있는 NestJS를 골랐습니다. 또 전 회사 백엔드가 Java Spring이었는데, NestJS는 모듈·컨트롤러·서비스로 나누고 의존성을 주입하는 구조가 Spring과 비슷해서, 나중에 Spring으로 넓힐 때도 개념을 그대로 가져갈 수 있다고 판단했습니다. 실제로 둘을 나란히 놓고 정리해 뒀습니다.

중구 문서(study-notes)에 NestJS ↔ Spring 비교표가 있음. TypeScript라서 골랐다는 부분은 문서에 적혀 있진 않으니, 본인 생각과 맞는지 확인하고 말하기.

T8DB는 왜 Neon(네온)으로 했나요?

Neon = PostgreSQL을 대신 띄워 주는 클라우드 서비스기준: 무료로 계속 운영할 수 있나표준 PostgreSQL → 옮기기 쉬움
아직 사용자가 없는 단계라, 비용 없이 화면·API·DB·배포까지 전체 흐름을 직접 겪어 보는 게 목표였습니다. Fly.io, Railway, AWS도 비교했는데, 무료로 계속 운영할 수 있는지를 기준으로 API는 Render, DB는 Neon을 골랐습니다. Neon은 표준 PostgreSQL이라, 실제 서비스로 키울 때 AWS RDS 같은 곳으로 옮겨도 연결 주소만 바꾸면 되게 해 뒀습니다.

꼬리 "실무라면?" → 자동 백업·특정 시점 복구가 되는 RDS나 Neon 유료. 무료는 백업·복구가 약함.

T9Sentry(센트리)는 왜 붙였나요?

Sentry = 운영 중 에러를 모아서 알려 주는 도구혼자 운영 → 사용자가 말해 주기 전에 알아야 함Next.js·NestJS 공식 지원 + 무료 등급
혼자 운영하다 보니, 사용자가 말해 주기 전에 서버나 화면에서 난 에러를 제가 먼저 알아야 했습니다. Sentry는 화면(Next.js)과 API(NestJS)를 둘 다 공식 지원하고 무료 등급이 있어서 골랐습니다. 처리하지 못한 500번대 에러만 보내고, 요청 내용이나 쿠키, 사용자 정보는 보내지 않게 설정했습니다.

공고의 "서비스 로그·장애 추적·모니터링"과 바로 연결됨. 꼬리 "실무라면?" → 에러만이 아니라 느려지는 것까지 보는 도구(Datadog 등) + 슬랙 알림.
